# 性能架构与验收预算

性能目标是让计划管理随时可用、后台安静、重型 AI 工作不拖慢界面。优先限制不必要的工作与资源增长，再用真实测量决定进一步优化。

**以下全部是设计目标，当前没有应用或性能实测结果。** 首次基线测量后可调整目标，但必须记录硬件、构建、数据规模、取舍和调整原因，不能将“未测”标为达标。

## 1 测量基线

参考设备：Windows 11 x64、4 核 8 线程或相当能力、16 GB 内存、SSD、1080p 显示器；电源模式、DPI、系统后台负载和运行时版本固定记录。macOS 与 ARM64 各自建立独立基线，不混合统计。

正常集为 1 万待办、10 万历史消息、10 个日历、10 万事件/实例记录、100 条自动化。大集为正常集的十倍，用于检查增长趋势和降级行为；不要求所有大集指标与正常集完全相同。

短操作重复至少 100 次记录 p50/p95/p99；启动至少 30 次，冷启动与热启动分开。空闲与泄漏使用固定持续场景。报告包括采样原始数据与构建标识，不能仅报告一次最佳值。

## 2 首轮性能预算

| 指标 | 初始目标 | 测量边界 |
| --- | --- | --- |
| 冷启动可交互 | p95 ≤ 2 秒 | 点击到今天页可操作；包含必要本机核心就绪，不等待外部引擎 |
| 热激活 | p95 ≤ 700 毫秒 | 已运行会话代理到主窗口可操作；与冷进程重启分别报告 |
| 快速捕获 | 本机确认保存 p95 ≤ 100 毫秒 | 不含自然语言模型解析 |
| 常规本机命令 | p95 ≤ 80 毫秒 | 输入到持久提交确认，含 IPC |
| 今日/项目第一页 | p95 ≤ 100 毫秒 | 正常数据集，有限条数 |
| 中文全文搜索 | p95 ≤ 250 毫秒 | 固定查询集，区分冷/暖缓存与分词策略 |
| 月视图切换 | p95 ≤ 150 毫秒 | 已连接核心，限定视窗与可见事件数量 |
| LAN 常规读写 | p95 ≤ 200 毫秒 | RTT ≤ 10 毫秒，含持久提交；不含外部 API |
| UI 交互帧 | p95 帧间隔 ≤ 16.7 毫秒 | 60 Hz 连续滚动场景；记录掉帧，不只看平均 FPS |
| 核心调度延迟 | p95 ≤ 2 秒 | 主机清醒且可用，到期到生成投递/运行意图 |
| 流式本地转发 | p95 ≤ 100 毫秒 | Adapter 收到片段到 UI 可见；模型首 token 延迟另报 |
| 基础后台空闲 CPU | 十分钟平均 ≤ 0.5% | 按整机总逻辑 CPU 容量计；无运行任务、无桌宠、无外部引擎 |
| 基础后台内存 | CoreHost ≤ 100 MiB，SessionAgent ≤ 40 MiB | 各进程 private working set，稳定五分钟后采样 |
| 主窗口内存增量 | ≤ 160 MiB | 默认页面稳定状态；基础进程合计目标 ≤ 300 MiB |
| 桌宠增量 | 空闲 ≤ 50 MiB，整机 CPU 平均 ≤ 0.5% | 限定大小的序列帧资源；动画另报峰值 |
| 24 小时稳定性 | 暖机后内存基线增长 ≤ 10%，无持续上升趋势 | 固定重复操作与长空闲，不以强制 GC 隐藏泄漏 |

外部引擎、MCP 子进程和本地 LLM 不计入“基础后台”预算，但必须同时报告**整棵进程树总量**、峰值、运行后回落和用户可设上限。排除基础预算不意味着可以无上限占用。

## 3 架构级优化

### 不在空闲期工作

CoreHost 保持必要状态，UI 关闭后释放主窗口进程。Pet 未启用时不加载图片与渲染器。Hermes、MCP 和编码执行器懒启动；空闲超时是否退出由实际会话恢复能力决定。

调度器维护最近到期队列和一个下一触发计时器，数据库保存事实；新增/修改调度通过事件重排计时器。设置低频有界对账以处理遗漏和时钟变化，不每秒全表扫描。

节点心跳、连接检查和订阅续期采用退避、抖动和合并。没有在线连接或变化时不刷新整个设置页。长期挂起的请求采用异步 I/O，不以阻塞线程轮询。

### 把重工作隔开

本地 LLM 推理、索引构建、大文件处理和外部命令不在 UI 线程。核心 Module 内部采用有界队列和有限工作者，避免无限 Task 创建与 ThreadPool 饥饿。

不引入每 Module 一个微服务；额外进程只为平台生命周期、可选资源或隔离带来明确价值。共用连接池、HTTP 客户端、序列化配置和短期缓存。

## 4 界面优化

列表同时做 UI 虚拟化和数据分页，避免“只虚拟化控件但仍把十万条正文载入内存”。WPF 的两种虚拟化并不等价，容器回收和模板设计也会影响开销。[WPF 控件性能](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls)

默认第一页 50 条，可见范围之外限制预取。会话正文只在需要时解析；图片先显示缩略图。切换页面取消旧查询，保留小型有界缓存；搜索输入约 200 毫秒防抖，并丢弃过期响应。

流式消息约 40–80 毫秒合并一次 UI 更新，仅更新活动段落，不为每个 token 重建整篇文档。未显示的运行不渲染富文本；最终状态和审批可立即刷新。

减少深层布局、重阴影、频繁透明大面积合成和昂贵绑定转换。减少动画、低电量与软件渲染模式有更保守配置。鼠标滚动不能触发同步数据库或网络访问。

## 5 数据库与文件

| 热路径 | 索引/处理方式 | 避免的问题 |
| --- | --- | --- |
| 今天/截止 | space_id、status、due_at 或 due_date 的合适组合 | 每次全表筛选 |
| 项目列表 | project_id、status、sort_key、id | 大 offset 与非稳定排序 |
| 会话消息 | conversation_id、ordinal | 一次加载全部消息 |
| 到期调度 | state、due_at，加租约筛选 | 所有任务逐条扫描 |
| Outbox | published/state、sequence | 重复扫描已消费事件 |
| 通知去重 | dedup_key 唯一索引 | 多入口重复投递 |
| 日历范围 | calendar_id、start/end 加有限重复展开 | 无限系列实例化 |
| 关键词检索 | FTS 或经过验证的中文索引 | 对每行正文做无界模糊匹配 |

索引不能盲目全字段覆盖；依据查询计划和写放大调整。SQLite 保持短事务和有限写入者，流式模型正文按块落盘，关键状态立即提交。禁止为速度关闭必要的持久性保证。

WAL 与同步等级、检查点频率、busy timeout 通过崩溃恢复和负载测试选择；锁定包含已知 WAL 修复的 SQLite 实际运行库版本，不能只看 NuGet 名称。网络共享数据库不在方案内。

中文搜索先验证标准分词对无空格中文的行为；候选为分词扩展或 n-gram 索引，明确准确率、索引体积与写入成本。向量库不是全文搜索的首期必需品。

附件与长日志流式读写，采用有限缓冲。不能把 Base64 大文件放进 SSE；元数据通过事件通知，内容由授权下载入口传输。备份和索引维护限速并在空闲执行。

## 6 队列与并发

| 工作种类 | 初始并发策略 | 过载处理 |
| --- | --- | --- |
| 同一工作区写任务 | 1 | 排队，显示等待原因 |
| 编码执行器 | 全局 1，可配置提高到 2 | 根据内存/CPU预算限制 |
| 本地 LLM 推理 | 每个推理实例 1 起步 | 不叠加加载多个大模型 |
| 云端模型 | 小型有限并发，按提供方限额 | 429 退避、预算与用户优先级 |
| 日历同步 | 每连接串行，不同连接有限并行 | 合并变更提示 |
| 邮件/推送 | 按渠道限流 | 退避、合并摘要，保留投递状态 |
| 数据库写入 | 短事务串行化协调 | 有限等待，过载显式返回 |
| 索引/嵌入/回顾 | 低优先级 1 | 活跃交互时推迟 |

初始队列容量按业务确定并可观察；内存队列满不能丢关键命令，必须写入持久待处理或拒绝并保留用户草稿。优先级包括交互、到期提醒、正在运行的结果、同步和维护；采用公平调度，防止维护永久饥饿。

所有工作具有截止时间、取消传播与资源上限。背压从慢客户端传播到事件缓冲；可以合并进度文本，不能丢审批或终态。

## 7 模型与 MCP

工具目录只加载相关能力；上下文优先精简引用，限量检索候选，不每轮追加整个文件夹。摘要按源版本缓存，不能在源内容变更后继续作为当前事实。

模型响应缓存只适用于无副作用、输入与权限范围相同的请求，默认不跨用户/空间共享。不能缓存“执行工具的结果”来伪造新的副作用完成。

MCP 进程按使用启动，设置最短驻留时间以防反复启停；状态不支持恢复的连接在用户活动期间保持。远程连接用共享 HTTP 池，工具 schema 按版本缓存。

本地模型加载不阻塞今天页。显存不足时排队、缩小配置或让用户改选，不静默切云端。界面显示引擎占用与队列，允许限制电池模式的重任务。

## 8 桌宠

透明窗口尺寸只覆盖宠物区域，资源按显示尺寸解码。空闲低帧、静止停帧、隐藏与锁屏停止更新；恢复后直接跳到当前状态，不补画所有错过帧。

限制图片总解码内存、透明面积和帧数；支持低功耗静态模式。硬件与软件渲染分别测量，禁止把 GPU 问题转化为持续满核 CPU 占用。

## 9 观测与优化流程

先分解耗时：启动发现、数据库打开、首屏查询、布局、外部连接。每条运行跟踪排队、引擎启动、首输出、工具等待、审批等待和完成，不能把用户审批等待算成执行器计算延迟。

使用 .NET 计数器/追踪、Windows 性能工具和必要的数据库查询分析；微基准只验证热点假设，不能代替端到端测试。采集 CPU、private working set、分配率、GC 暂停、线程池、句柄、连接数、队列长度、数据库锁等待和磁盘增长。

优化顺序：删除无用工作 → 缩小数据与刷新范围 → 索引与批量 → 有界缓存 → 进程与算法调整 → 必要时专用原生实现。每次优化保留对照数据，达标后不为抽象“更快”无限扩大范围。

## 10 分阶段性能门槛

S0 建立空壳与进程基线；S1 关注捕获、冷启动和本机 CRUD；S2 测日历展开、休眠补偿与空闲；S3–S5 测长会话、流式、队列与外部进程回收；S6–S8 测多渠道、多设备与 LAN；S9 做 24 小时稳定性、安装与大集趋势。

普通非热点改动不要求全套性能重跑。影响热路径、依赖升级、数据形状或进程生命周期时运行相关场景；出现超标先定位并修复，再扩展范围。

## 11 明确不采用的捷径

不以减少持久化、跳过权限、无限缓存、全量预加载、启动时加载所有 LLM、关闭 TLS 校验或丢弃终态事件换取性能。NativeAOT、裁剪和激进发布选项必须按具体进程兼容性验证，不能假定整套 WPF 与动态插件依赖都可直接开启。
